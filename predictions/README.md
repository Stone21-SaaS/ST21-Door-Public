# ST21-Door 公开预测栏 · 玩法与规则

> **这是什么**：一个公开的短期预测栏。家里的人各挂几条预测，**让时间来打分**。
> **就玩，但玩得认真** —— 认真指的是：**规则先定死，然后不许跟着结果改。**
>
> **发布状态**：**第一期已正式启动**（2026-10-11）。10 条预测已公开冻结；规则与结算口径见本文件及 `index.md`。首批服务端发布时间的独立证据尚未闭环，详见 `index.md`，该限制不被视为已解决。

## 1. 一条预测长什么样

文件顶部是 front-matter，**共 10 个字段**（缺一不可）：

| 字段 | 说明 |
|---|---|
| `id` | 预测编号（同时是文件名） |
| `author` | 谁挂的（署名） |
| `content_sha256` | 本预测内容的哈希，按 **R-a** 算法算（见 §8） |
| `claim` | 预测内容，一句话说清 |
| `probability` | 主观概率，**两位小数**，写成字符串（如 `0.45`） |
| `deadline_utc` | 截止时间，**完整 UTC 时间戳**（`YYYY-MM-DDTHH:MM:SSZ`） |
| `criterion` | **判定标准：二分 + 指向外部来源**（怎么写算 TRUE、怎么写算 FALSE） |
| `criterion_source` | 判定去**哪里看**（官方页 / 正式文件 / 原始数据） |
| `resolver` | 到期由谁查证 |
| `status` | `OPEN` / `TRUE` / `FALSE` / `VOID` |

**解析约定（写脚本的人看）**：字段值取**该行 `: ` 之后的全部内容，原样到行尾**；
**不要折行**（值里不换行），否则哈希对不上。

**`status` 结算时的附加约定**：若记为 `VOID`，在正文加一行
`VOID原因：<为什么无法核验>` —— 打分脚本会把原因一并列出（**原因不属于 10 个字段，不参与哈希**）。

## 2. 规则 R-a ～ R-f

**R-a 哈希**
`content_sha256 = SHA-256( JSON 序列化( [id, author, claim, probability, deadline_utc, criterion, criterion_source, resolver] ) )`

- 8 字段取 front-matter **字符串原样**（含换行原样，由 JSON 转义确定性处理）
- `probability` **写两位小数**（如 `0.45`、`0.60`），**取字符串形式，不做数值转换**
- JSON 数组，`separators=(',',':')`，`ensure_ascii=False`，**UTF-8 编码**
- **排除**：`content_sha256` 自身、`status`

**R-b 服务端时间**
文件**不预填发布时间**。推送后**以 GitHub 服务端可核验的提交时间为准**，
把 **commit SHA 与平台时间**追加记入 `index.md` 的发布记录表。
**客户端 commit 时间不得替代服务端时间。**

**R-c Brier 打分**
只纳入已结算的 `TRUE`/`FALSE`；`VOID` 不计分，但**保留数量与原因**；
**按预测者逐项计算并披露有效样本数**。同来源、同时间窗口的条目可列作**相关性提示**，但不得仅凭来源和截止时间相同就认定为同一事件，也不得认定它们相互独立。

**R-d 时间戳**
全部使用**完整 UTC 时间戳**（`YYYY-MM-DDTHH:MM:SSZ`）。

**R-e 历史草案**
`working/predictions-discussion.md` 第三节的 **P-2026-001–003 为小曜早期草案**，
**已被 007–009 替代，不计入第一期、不计分。**

**R-f 统一窗口**
凡判据含"在窗口内 / 至截止日发生、发布、作出"等**事件性表述**的，
**事件时刻须落在 `[T_publish, deadline_utc)` 半开区间内**；
`T_publish` = 该条实际推送后 **GitHub 服务端确认的发布时间**（推送后写入索引，**事先不预填**）。
**点状态型判据**（008 / 012 的榜单日检查）**不受 R-f 影响**。

## 3. 宪法（清岚）

1. **预测可以错，规则不能跟着结果变。**
2. **错了不删、不改；改判断另发新预测。**
3. **无法核验记 `VOID`。**
4. **命题必须可判定**：发生 / 未发生的条件 + 截止时间 + 证据来源。
5. **证据规则预先确定**：**官方公告 > 正式文件 > 原始数据**。
6. **`criterion` 必须二分、指向外部来源。**

---

## 4. 证据规则

- 判定**只看** `criterion_source` 指向的来源；**媒体报道只用于"发现"，不作为判定依据**（除非该条明确写了媒体来源，如 009）。
- 判据里**排除什么**（"以下不算命中"）**与包含什么同等重要** —— 一期多条已写死排除项，结算时照此执行。
- **不做解释、不做推断**：只核对"该来源是否出现了判据所说的事实"。
  信息不足以判定 → **`VOID`**，**不拿邻近日/相邻榜单替代**。

---

## 5. Brier 打分口径与脚本

- 单条得分：`(probability - outcome)^2`，其中 `TRUE = 1`、`FALSE = 0`。
- 个人 Brier = 该预测者所有已结算条目的**平均**；同时披露**有效样本数 n**。
- `VOID` **不计分**，单独统计**数量与原因**。
- **同来源、同时间窗口的预测**：**分别计分**；脚本会把这类条目**列出来**，
  但那只是**相关性提示** —— **不认定它们属于同一事件，也不认定它们相互独立**。
  （判据：`criterion_source` 与 `deadline_utc` 相同。**这只是提示，不是认定。**）

用法：

```bash
python3 predictions/score_brier.py                 # 正常打分
python3 predictions/score_brier.py --json          # JSON 输出
python3 predictions/score_brier.py --verify-hashes # 只做 R-a 哈希复核（复核者用这个）
```

**复核者请用 `--verify-hashes`**：它从落盘文件重算每条的 `content_sha256` 并与文件内声明值逐条比对，
输出 `MATCH / MISMATCH` 与汇总；**全部一致时退出码为 0**。
**不必采信任何人的"已核过"结论 —— 自己跑一遍即可。**

## 6. 节奏（霜卿）

- **静态文件 + 低频结算**：**每月固定一天批量结算**。
- **门的事优先。**
- **不在云机加爬虫 / 定时器 / 自动打分。**

---

## 7. 红线

- **`public` = 永久公开**：**无凭据、无未公开材料、无内部内容。**
- **推送失败要重试并留痕**，**绝不把"没推上去"含糊成"发过了"**。
- **不把预测写成对外承诺。**
- **不用自家门的数据**（自己给自己打分容易失真）。
- **不预测自己正在做的事**（利益冲突）。

## 8. R-a 复算代码（README 必须附）

```python
import json, hashlib

# id_, author, claim, probability_str, deadline_utc, criterion, criterion_source, resolver
fields = [id_, author, claim, probability_str, deadline_utc, criterion, criterion_source, resolver]
canonical = json.dumps(fields, ensure_ascii=False, separators=(',', ':'))
sha256 = hashlib.sha256(canonical.encode('utf-8')).hexdigest()
```

**逐条核对示例**（读某个 `P-*.md` 的 front-matter，填进上面 8 个变量，算出的 64 位十六进制应等于该文件的 `content_sha256`）。

## 10. 网友赛道（对外投稿）

> 本章 **2026-10-11** 新增。机制设计由清岚最终确认通过；资源与节奏由霜卿复核通过。
> **第一期 10 条（家里人）按原规则不变、独立运行**，不受本章影响。

### 10.1 定位与机制

- 先生拍板："既然玩就玩大一点，我们自己人不插手，让网友来。"
- **门不预测未来。门只判结算诚实性**：投稿者的"命中 / 未命中"主张，是否得到其所附证据的支持。
- 门的三元组映射：`Task` = 投稿时冻结的 `criterion` + `criterion_source`；
  `Input` = 运维按冻结规则整理后的结算证据字符串；
  `Output` = 投稿者的结算主张。
- 总纲：**门实际判了什么，我们就公布什么；它没有做过的事，我们绝不替它宣称做过。**

### 10.2 最终规则

**R1 verdict 对外口径（中性，不做人品指控）：**

- `ALLOW`：结算主张得到所提交材料支持。
- `BLOCK`：结算主张超出了所提交材料能够支持的范围。
- `NEEDS_EVIDENCE`：现有材料不足以作出上述判断。

**R2 公开范围：** 只公开原始 verdict；不承诺公布理由；
不得事后替门编写理由并声称为门的原始判定。

**R3 trial 额度：** 网友赛道的所有门判定（投稿准入 + 到期结算）均计入
trial 撞门计数，按现有 trial 额度统一管理（先生："该领就领，这也是撞门，方便我们计数"）。
Trial 凭据约 24 小时有效、每凭据最多 100 次请求，申领与管理走现有流程。

**R4 职责边界：**

- **门**：只负责判定输入三元组，按 Five Core 机械执行。
- **运维（小曜）**：按预先公开的规则组织输入、保存原始 verdict、公布结果。
- **人工**：仅做本方案明确允许的来源合规检查与证据抽查；不得改写门 verdict；
  一切人工动作留痕并公开说明。

**S1 投稿准入分工：**

- 运维按公开规则做准入初筛（字段完整性、格式、概率与截止时间窗口、
  明显违规内容如人身攻击/凭据/内部信息钓鱼/与预测无关），留痕。
- 门仅对通过初筛、已结构化的投稿执行其能力范围内的支持关系检查；
  **不承诺**识别 spam / 隐私 / 恶意等通用审核能力。
- **红线：凡未经验证的能力，一律不写成门的功能。**

**S2 + 第八节 结算证据规则：**

1. 投稿者在原 issue 下提交结算（主张 TRUE/FALSE + 证据链接）。
2. 运维按投稿时冻结的 `criterion` / `criterion_source`，把证据内容整理为实际输入材料：
   - 选取规则**事先冻结**，**严禁在看到 Door 判定结果之后再选择、更换材料**；
   - 转录按预先公布的固定规则，**不得改写、增删原意**；
   - 如规则允许摘录，必须按固定规则确定范围，并保留来源原文或可复核的存档，
     以便外部核对是否存在选择性遗漏。
3. **先冻结输入，再跑门判定**；**原始输入三元组与原始 verdict 一并存档公开，事后不得改动**。

### 10.3 投稿方式与节奏

- 投稿方式：本仓 **Prediction issue 模板**（`.github/ISSUE_TEMPLATE/prediction.yml`）；
  字段沿用第一期 front-matter；判据须二分、可外部核验；deadline **1–6 个月**（AGI 类暂不收）。
- 邀请帖正文见 [`INVITATION.md`](INVITATION.md)。
- **每月与第一期合并批量结算一次**，不另起节奏。
- 无奖金，纯玩；公开 Brier 榜（只计 `TRUE`/`FALSE`）。
- **每人每月 ≤ 5 条**，靠运维人工执行，超量顺延或驳回。
- **一次 `ALLOW` 只表示"结算主张得到所提交材料支持"，不表示事实绝对正确。**
- 第一期 10 条（家里人）按原规则不变，独立运行。

### 10.4 运维清单（霜卿）

- **结算日**：每月 **11 日 UTC**，与第一期合并批量。
- **三元组装法**：`material` = 证据摘录 / `task` = 结算主张说明 / `model_output` = 主张陈述。
- **串行调用门接口**，每条间隔数秒；失败有限次重试；
  仍失败标"**结算技术未完成**"，**不得擅自记为 TRUE/FALSE**。
- **存档公开**：input 三字段 + verdict + trial 调用时间（**无密钥、无内部路径**）。
- **结算日使用新领 trial 钥**，避开试用高峰。
- **准入初筛日常进行**，可攒到结算周统一过门。
